# V1 Plan — Family Camera App

Product plan for the first usable version of the family camera application,
built on the validated POC technical base.

`docs/PLAN.md` remains the POC technical history and decision log; this
document is the implementation plan for the first family-facing version.

## 1. Product Goal

A family member opens the app, sees the home cameras, taps a camera, and
watches its live video. No family member should need to understand Tailscale,
Frigate, VPNs, IP addresses, DNS, or network transports. Connectivity is
transparent.

The app is installed and configured by an administrator on a small number of
family devices. There is no provisioning backend, no self-service enrollment,
and no account management.

## 2. User Experience

**Product principle (explicit): "Infrastructure is an implementation detail."**

The normal user never sees LOCAL/TAILSCALE, Tailscale, Frigate, or network
terminology. Visible states use product language only:

- Connecting
- Live
- Camera unavailable
- Try again

The normal flow is:

```text
Open the app
  -> see the cameras
  -> tap a camera
  -> watch live video
```

Transport details, connection internals and diagnostics belong to an
advanced Diagnostics screen, not to the normal flow.

## 3. Architecture Baseline

Keep the proven POC module boundaries. No new network/playback stack is
introduced.

```text
app/                      Android application (Kotlin + Jetpack Compose)
  ui/                     Compose screens (Home, Live View, Diagnostics, Settings)
  navigation/             minimal screen navigation
  controller/             shared connection/session state (extracted from HomeScreen)

core/connectivity/        Application-oriented connectivity state (unchanged)
core/frigate/             Frigate HTTP integration (unchanged + camera discovery)
core/playback/            Android playback implementation (unchanged)
native/tailscale/         Go/Tailscale integration and Android bridge (unchanged)
```

### 3.1 Reused unchanged

- `native/tailscale` (Go `tsembed` module, `build-android.sh`, gomobile AAR)
- `native/tailscale` `TailscaleBridge` + `TsnetGatewayImpl` (TsnetGateway)
- `core/connectivity` (`ConnectivityState/Status`, `HttpBytesGetter/Result`)
- `core/frigate`: `FrigateConnectionManager` (local-first fallback strategy and
  node lifecycle policy), `FrigateConfig`, `FrigateConnection`, transports,
  `TransportKind`, `FrigateVersionProbe`, `Go2RtcStreams` (stream discovery,
  HLS/fMP4 URL, session resolution), `bytesGetterFor`, getters
- `core/playback`: `LiveStreamPlayer`, `PlaybackStatus`, `PlayerMetrics`,
  `HttpBytesDataSource`, `HttpBytesDataSourceFactory`
- `MainActivity` keep-screen-on and `configChanges` handling
- backup/data-extraction exclusion rules (Tailscale state excluded from cloud
  backup)
- Diagnostics logging/metrics primitives (time to first frame, error count,
  bytes, recoveries, transport-switch logs)

### 3.2 Refactoring required for product use

- `app/ui/HomeScreen.kt` currently owns connection state, the LiveView and the
  controls in one screen. It is split into a shared connection/session
  controller (reusing `FrigateConnectionManager` as-is) plus separate screens.
- Frigate URL moves from build-time `BuildConfig` + `rememberSaveable` to
  persisted admin configuration (V1.1) using Preferences DataStore (see
  Section 12).
- Node hostname (`poc-camera` today) becomes an internal value: a stable
  auto-generated name derived from the persistent node identity, never part of
  the normal configuration flow. Any debug override lives only in
  Advanced/Diagnostics.
- `core/frigate` gains a camera-discovery function (additive; no existing code
  rewritten).
- `app/navigation` is implemented (currently an empty placeholder).

## 4. V1 Scope

Delivered in V1:

- First-run administrator setup (Frigate URL, Tailscale enrollment when
  needed, connectivity check)
- Camera discovery from Frigate (no hardcoded camera names)
- Home screen with camera cards (display name, thumbnail, status)
- Live View with a single live stream (proven HLS/fMP4 playback)
- Transparent connectivity (LOCAL first, embedded Tailscale fallback, return
  to LOCAL stops Tailscale)
- Diagnostics screen with sanitized copy
- Settings / Advanced screen for the administrator

Explicitly excluded (see Section 17 for the full list): recordings timeline,
event history, object detection UI, push notifications, simultaneous live
streams, camera administration, Frigate configuration, file/media apps, SSO,
user accounts, cloud backend, self-service provisioning, iOS, Android TV,
WebRTC migration, VpnService migration.

## 5. Initial Setup

First-run flow, administrator only. Shown until setup succeeds; after success
the normal flow starts and infrastructure details no longer appear.

Minimum responsibilities:

1. Enter the Frigate server URL (a single URL, used by both paths, as in the
   POC).
2. Test connectivity: run the proven `FrigateConnectionManager.connect()`
   probe. Show a simple result (connected / failed / needs enrollment).
3. When the embedded node needs enrollment, start it and present the
   enrollment URL (existing `TailscaleAuthRequired`/auth URL flow) with an
   "Open login URL" action and a Retry.
4. On success, persist the configuration and enter the app.

Design rules:

- Setup must not embed any reusable Tailscale auth key (enrollment stays
  interactive, admin-assisted).
- Setup is a gate, not a settings screen: after it completes, normal use never
  asks about infrastructure again.
- Re-running setup (edit server URL) lives in Settings and is the
  administrator's path to change the server.
- Setup never asks for infrastructure details such as the Tailscale node
  hostname; it is auto-generated internally.

## 6. Camera Discovery

The app obtains the camera list from Frigate at runtime. No hardcoded camera
names.

### 6.1 Frigate API

- **Camera list:** `GET /api/config` (camera keys and per-camera metadata such
  as `enabled` and the friendly/display name). Verify the exact shape on the
  installed Frigate 0.17.1 during V1.2, including which field carries the
  friendly name; parse only the fields the app needs.
- **Stream availability:** `GET /api/go2rtc/streams` (already implemented) maps
  camera names to playable go2rtc streams.
- **Thumbnail:** `GET /api/{camera}/latest.jpg` (verify the exact snapshot
  endpoint on the installed version). Thumbnails are best-effort: a missing
  or failing thumbnail does not block the card.
- **Server version:** `GET /api/version` (already implemented; shown in
  Diagnostics).

No generic Frigate SDK is built. Only the endpoints above are used.

### 6.2 Minimal camera model

```text
Camera(
  id: String,              // Frigate config key / go2rtc stream name
  displayName: String,     // Frigate friendly name, camera key fallback (see 6.3)
  enabled: Boolean,        // from Frigate config
  playable: Boolean,       // resolved against /api/go2rtc/streams
  snapshotUrl: String?     // thumbnail source, when available
)
```

### 6.3 Display names (Frigate is the source of truth)

Frigate is the source of truth for the camera's friendly/display name.

- The camera **key** (the `id` field) is the stable technical identifier; it is
  always kept as the internal identifier and go2rtc stream name.
- The **display name** shown in the app comes from the friendly name field in
  the Frigate camera configuration payload. During V1.2 the exact field name is
  validated against the real Frigate 0.17.1 payload.
- If the friendly name is **absent or empty**, the camera key is used as the
  display name (fallback). No other transformation is applied.
- Friendly names are **not persisted** locally and there are **no local
  overrides**; the display name is re-resolved on every discovery. No name
  configuration exists in Settings.

The app never shows raw infrastructure terms in the normal flow; the camera
key is already a plain word, so the fallback needs no transformation.

### 6.4 Disabled and unavailable cameras

- **Disabled** (`enabled: false` in the Frigate config): excluded from Home.
- **Unavailable** (enabled but with no matching go2rtc stream, or thumbnail/
  probe failing): shown in Home with a "Camera unavailable" state and a
  Try again action.
- Live View opens only playable cameras; an unavailable camera navigates to
  the unavailable state instead of a dead player.

## 7. Home Screen

- Presents the discovered cameras as a responsive grid of minimal cards.
- Card content: display name (Frigate friendly name, see 6.3),
  thumbnail/snapshot (best-effort), status
  (available / unavailable) when useful.
- Tapping an available camera opens Live View.
- Home does **not** start live streams for all cameras; no thumbnails are
  live video, and the Home screen stays light.
- Refresh action re-runs discovery (config + streams) without re-probing the
  connection transport.
- Connection state shown in product language (Connecting / Live / Camera
  unavailable / Try again); never LOCAL/TAILSCALE.

## 8. Live View

- Opened by tapping a camera card; shows one live stream at a time.
- Reuses the proven playback architecture: `LiveStreamPlayer` +
  `HttpBytesDataSource` over the transport getter selected by the shared
  controller.
- Required states: loading, playing, unavailable/error, retry.
- Back navigation releases the player (existing `DisposableEffect` teardown;
  bytes must stop, verified on device).
- Fullscreen: add if it can be done with small scope (hide app bars / system
  bars via the existing window flags); otherwise skip for V1.
- The transport is not changed: HLS/fMP4 through the Frigate `/api/go2rtc/`
  proxy stays unless a concrete V1 requirement proves otherwise.

## 9. Connectivity

Preserve the proven policy exactly:

```text
Frigate reachable on the LAN            -> LOCAL (Tailscale stays stopped)
Not reachable on the LAN                -> start embedded node -> TAILSCALE
Return to the LAN                       -> confirm LOCAL -> stop Tailscale
```

- The UI (Home, Live View) shows only product states.
- LOCAL/TAILSCALE and transport-switch details appear only in Diagnostics.
- Existing behaviors stay: network re-probe with settle delay, no churn on
  cellular handovers, unbounded recovery over TAILSCALE, bounded recovery over
  LOCAL, pause-free Play/Stop controls, keep-screen-on, rotation survival.

## 10. Diagnostics

Advanced screen for the administrator, preserving the POC observability.

Display:

- Frigate connectivity
- Tailscale state (disconnected / authenticating / connecting / connected /
  failed)
- Selected transport (LOCAL / TAILSCALE) — the only place these terms appear
- Playback state
- Last playback error
- Time to first frame
- Server version (`/api/version`)
- App version
- Diagnostics counters: errors, bytes, recoveries, transport switches

Actions:

- **Copy diagnostics:** produces a sanitized plain-text report.
- The copied content must never contain secrets, authentication/enrollment
  URLs, tokens, or other sensitive credentials. A dedicated report builder
  with tests guarantees this (see Section 12).
- Retry connection from here is allowed (admin convenience), but the normal
  flow has its own Try again.

## 11. Settings / Advanced

Deliberately small, administrator-oriented:

- Frigate server URL (edit + connection test)
- Enrollment / Tailscale reset (re-run enrollment; reset clears node identity
  and re-enrolls interactively)
- Diagnostics entry
- Debug-only node hostname override (Advanced only; the normal value is
  auto-generated and never part of the standard flow)
- App information (version, build)

Normal family use should rarely require this screen. It is reachable from
Home via a discreet entry point.

## 12. Security

Minimum documented guarantees:

- **No reusable Tailscale auth key in the APK.** Enrollment stays interactive
  (existing auth URL flow). Never embed a reusable key, now or later.
- **No secrets written to logs.** Remove the POC log line that prints the
  enrollment auth URL (`tsembed login required` context is fine, the URL is
  not); keep logs free of auth URLs, tokens and credentials.
- **Tailscale identity/state excluded from cloud backup.** Already enforced by
  `backup_rules.xml` / `data_extraction_rules.xml` (everything excluded,
  including `filesDir/tailscale`); keep it that way.
- **Configuration persisted with the standard Android mechanism.** Frigate
  URL and normal settings use AndroidX Preferences DataStore (plaintext, not
  encrypted). `EncryptedSharedPreferences` (AndroidX security-crypto) is
  explicitly rejected: these values are configuration, not secrets, and
  encryption for precaution adds a deprecated, heavyweight dependency.
  Tailscale state stays in `filesDir/tailscale` (already backup-excluded).
- **Diagnostics sanitized before copy.** The copy builder only includes the
  allow-listed fields; a unit test asserts the report never contains the auth
  URL or token-shaped strings.
- **No Frigate service exposed publicly** to support the app. The app reaches
  Frigate only through the LAN or the embedded tailnet path.
- No new security framework is introduced: DataStore is a plain configuration
  mechanism, not a security library.

### 12.1 Data classification and persistence

**Configuration (not sensitive, plaintext via Preferences DataStore):**

- Frigate server URL
- Normal app settings
- Display names come from Frigate at runtime; not stored locally (V1 has no
  overrides)

These are not secrets; the standard Android preferences mechanism is
appropriate and encryption is deliberately not added for precaution.

**Sensitive (never written to app config):**

- Tailscale node identity and connection state: owned entirely by the existing
  Tailscale module storage (`filesDir/tailscale`), already excluded from cloud
  backup and data extraction. Unchanged.
- Enrollment/auth URL: one-time and transient; never persisted, never logged.
- Reusable auth keys and tokens: never embedded in the APK or stored on
  device.

## 13. Lifecycle

Preserve and extend the POC lifecycle guarantees to a multi-screen app:

- **Live View teardown:** leaving the Live View (back navigation, connection
  loss, transport switch) releases the player and stops bytes (existing
  `DisposableEffect`). Only one live stream exists at a time.
- **Screen off:** `ON_STOP` releases the media source (no background data);
  `ON_RESUME` re-establishes a fresh go2rtc session (existing behavior).
- **Rotation:** handled via `configChanges`; no activity recreation, no
  playback restart.
- **Network switch:** re-probe with settle delay; healthy playback is never
  restarted; dead sessions recover (existing behavior).
- **Tailscale node:** only started by the fallback path, stopped when LOCAL is
  confirmed again (existing policy in `FrigateConnectionManager`).
- **Process restart:** node identity persists in `filesDir/tailscale`
  (verified in the POC). App settings persist via Preferences DataStore.

## 14. Error Handling

- Transport/network failures keep being surfaced as retryable `IOException`
  from `HttpBytesDataSource`; ExoPlayer retries transiently; fatal errors
  surface to the player state.
- Playback recovery: unbounded over TAILSCALE (every error re-establishes a
  fresh go2rtc session), bounded over LOCAL — current behavior, unchanged.
- User-visible errors use product language (Connecting / Live / Camera
  unavailable / Try again). Raw messages appear only in Diagnostics (last
  playback error) and logcat.
- Discovery failures (config, streams, thumbnails) are best-effort: Home still
  renders, unavailable cards show their state.
- The last error is kept in the shared controller state so Diagnostics can show
  it after the fact.

## 15. Testing Strategy

- Existing gates stay: `./gradlew test lint :app:assembleDebug`, `go test
  ./...`, `go vet ./...` in `native/tailscale/go`.
- New unit tests:
  - camera-list parsing from a sample `/api/config` payload
  - display-name resolution: Frigate friendly name present -> used as display
    name; friendly name absent -> camera key fallback; friendly name empty ->
    camera key fallback
  - settings persistence round-trip (Preferences DataStore)
  - diagnostics copy sanitization (never contains auth URL/tokens)
- Playback/connectivity behavior is unchanged, so the existing test suite must
  stay green without modification.
- Every milestone has physical-device acceptance criteria (see Section 18).
- The final V1 validation runs on the family devices with the admin + family
  member scenarios (Section 19).

## 16. Technical Debt

Carried from the POC, documented and not resolved in this task:

- **Patched Go toolchain for tsnet on Android 11+** (`netlinkrib: permission
  denied`, CL 507415 fallback in `go-patched/`). Build depends on the patched
  toolchain; standard toolchains fail `tsnet.Start()` on physical devices.
  Watch for an upstream merged fix; until then keep `docs/TOOLCHAIN_PATCH.md`
  current.
- **Whole-response buffering** in `HttpBytesDataSource`: acceptable because
  every HLS request is bounded (playlist/init/segment). Not valid for
  progressive or long-lived streams; revisit only if the transport changes.
- **Plain HTTP (`usesCleartextTraffic=true`):** LAN and tailnet origins are
  HTTP. Production should move to TLS (Frigate TLS or a private reverse
  proxy). Not a V1 blocker; keep documented.
- **Auth URL in logcat:** existing POC logs the enrollment URL; removed in V1
  (Section 12) — this is a fix, not an accepted debt.
- **Single-camera POC focus:** camera grid, discovery and thumbnails are new
  V1 work; the playback path itself is reused as-is.
- **Live View landscape clipping (V1.4, UI/polish debt):** rotating the Live
  View to landscape clips part of the content; the screen has no
  scroll/adaptive layout for the shorter available height. Playback continues,
  no crash and no networking/lifecycle regression. Deferred to a later
  UI/polish milestone (not blocking V1.4).

### V1.2 — Camera discovery

**Status:** IMPLEMENTED AND VALIDATED (2026-08-12) — implementation and unit
-tests green; physical-device validation completed successfully on LAN and
outside the home LAN.

- **Goal:** the app lists the configured cameras from Frigate.
- **Scope:**
  - `core/frigate` camera discovery from `/api/config` (minimal model)
  - validate on the real Frigate 0.17.1 payload which field carries the
    friendly name
  - display-name resolution: Frigate friendly name used as the display name;
    camera key as fallback when the friendly name is absent or empty; no
    persistence, no local overrides
  - disabled cameras (`enabled: false`) excluded at the discovery boundary
  - per-camera playable resolution against `/api/go2rtc/streams`: an enabled
    camera is `playable` only when a stream whose name exactly equals the
    camera key exists; matching is by camera id, never by stream order. A
    camera without its stream stays in the result with `playable = false`. If
    `/api/go2rtc/streams` fails after `/api/config` succeeds, the cameras are
    preserved with `playable = false` and the failure is recorded
    (`streamsWarning`) for diagnostics.
  - unit tests with a sample config payload
- **Non-goals:** Home UI, thumbnails (`snapshotUrl`), live playback changes,
  local name overrides, name configuration in Settings.
- **Tests:** camera-list parsing, enabled/disabled exclusion, display-name
  resolution tests (friendly name present -> used; absent -> key fallback;
  empty -> key fallback), and the playable matrix (enabled + matching stream ->
  playable; enabled without stream -> kept with playable=false; multiple
  cameras with a subset of streams; disabled exclusion; no enabled cameras ->
  Empty; empty streams -> Loaded all playable=false; streams endpoint failure
  -> cameras preserved with warning; matching by id not by first stream).
- **Physical-device acceptance:** on LAN and outside, the app resolves exactly
  the enabled cameras; disabled cameras are excluded; Frigate display names
  show correctly, with the camera key used as fallback when the friendly name
  is absent or empty; every enabled camera resolves `playable=true` against the
  real `/api/go2rtc/streams` (a camera key that diverges from its stream name
  would be reported as a divergence instead of guessed).
- **Validated (physical device, 2026-08-12):** the acceptance criteria above
  were confirmed on the real install. Exactly the enabled cameras (`backyard`,
  `hall`, `gate`) appeared; the disabled `garage` camera did not. Friendly
  names rendered in the provisional list; no camera key diverged from its
  go2rtc stream name, so all enabled cameras resolved `playable=true` on both
  LOCAL and TAILSCALE transports.

**Findings from the real Frigate 0.17.1 payload:**

- `GET /api/config` returns the full `FrigateConfig` dump. Cameras live under
  `cameras`, keyed by the camera name. The friendly-name field is
  `friendly_name` (omitted when unset because `exclude_none=True`). The enabled
  field is `enabled` (Boolean, default `true`).
- `/api/config` requires passing through Frigate's `/auth` endpoint
  (`allow_any_authenticated()`). Anonymous access works only when Frigate auth
  is disabled (current install). This is recorded as a risk in `docs/PLAN.md`.

### V1.3 — Home screen

**Status:** DONE (2026-08-12) — implementation, unit tests and physical-device
validation completed.

- **Goal:** family member sees the cameras.
- **Scope:**
  - camera card grid (display name, snapshot thumbnail, status)
  - refresh action; unavailable-card state and Try again
  - no auto live streams; single-stream guarantee at navigation level
  - `Screen.Live` route and per-camera navigation shell (the player itself is
    V1.4, but the route and `LiveScreen` container are introduced here so the

    refresh counter (`FrigateSnapshotKeyer`), so manual refresh fetches a fresh
    snapshot while normal navigation benefits from caching.
  - The enrollment-during-network-switch bug is fixed: when a Live session loses
    LOCAL connectivity and the Tailscale fallback requires enrollment, the app
    routes to the existing `SetupScreen` enrollment flow instead of falling back
    to a failed Home state. The fix is a single navigation decision in
    `AppRoot`'s `Screen.Live` branch (see Decision Log in `docs/PLAN.md`).
- **Non-goals:** multiple simultaneous streams; camera management; polished
  player states (V1.4).
- **Tests:** card/state logic tests (`CameraCardTest`, `CameraGridSectionTest`);
  thumbnail fetcher/keyer tests; Live navigation decision tests
  (`AppRootLiveDestinationTest`); existing suite green.
- **Physical-device acceptance:** cards render thumbnails on LAN and outside;
  unavailable cameras show their state; Home stays responsive and light.
  Validated on a physical device: Wi-Fi LOCAL -> mobile data with an
  unenrolled node correctly promotes the administrator to the enrollment

### V1.4 — Live view integration

**Status:** DONE (2026-08-14) — implemented and physically validated. All 10
validation scenarios passed on a physical Android device. One non-blocking
visual limitation recorded as UI/polish debt (Section 16).

- **Goal:** tap a camera and watch live video using the proven playback path.
- **Scope:**
  - Live View screen wired to `LiveStreamPlayer` and the shared controller
  - loading / playing / unavailable / error / retry states
  - back navigation releases the player
  - fullscreen toggle (small scope, or explicitly dropped)
- **Implementation notes:**
  - The Live View plays **exactly the selected camera's** go2rtc stream:
    `Go2RtcStreams.streamNameForCamera` resolves the stream by
    `camera.id == stream name` equality (never a "first stream"). The removed
    `firstStreamName`/`firstTopLevelKey` APIs no longer exist anywhere in the
    V1 flow. A selected camera without a matching stream surfaces a
    "Camera unavailable" state with Try again instead of a dead player.
  - `AppRoot` resolves the Live camera with the pure `resolveLiveCamera`
    (selected camera wins, exact-id discovery fallback for restarts). The Live
    screen title uses the Frigate `displayName` (friendly name, camera key
    fallback), never a raw camera id.
  - The network-change listener stays registered while live video is shown
    (the POC behavior), so turning on home Wi-Fi while watching re-probes
    local-first and switches back from Tailscale to LOCAL without interaction.
    This restored the POC transport-switch behavior that a separate Live
    destination had dropped (see Decision Log in `docs/PLAN.md`).
  - Recovery is fully automatic and invisible: every playback/discovery
    failure is retried with a fresh go2rtc session and no error UI.
  - Playback/lifecycle/metrics behavior is unchanged from the validated POC.
- **Non-goals:** transport or player changes; fullscreen toggle (explicitly
  dropped in V1.4; a hardware-back/rotation-friendly player surface is left to
  a later milestone).
- **Tests:** `TransportAndGo2RtcTest` (streamNameForCamera by exact id, order
  independence, missing/empty streams -> null, non-2xx propagation),
  `ResolveLiveCameraTest`, `LiveViewTest` (Robolectric/Compose: per-camera
  stream resolution, unavailable state, player released on leave); full suite
  green (`./gradlew test lint :app:assembleDebug`, `go test ./...`,
  `go vet ./...`).
- **Physical-device acceptance (2026-08-14, all 10 scenarios passed):**
  - per-camera playback by `cameraId` validated (selected camera plays its own
    go2rtc stream, not a "first stream");
  - LOCAL -> TAILSCALE switch validated (leaving the home LAN falls back to the
    embedded node);
  - TAILSCALE -> LOCAL switch validated (home Wi-Fi on re-probes local-first
    and switches back);
  - embedded Tailscale node stopped after LOCAL is confirmed;
  - playback stability validated (5-minute stable live video; network-switch
    recovery; back navigation stops bytes; rotation keeps playback; time to
    first frame logged);
  - automatic invisible recovery validated.
- **Known limitations (recorded as UI/polish debt in Section 16, not
  blocking):** rotating the Live View to landscape clips part of the content;
  the screen has no
  scroll/adaptive layout for the shorter available height. Playback continues,
  and there is no crash or networking/lifecycle regression. Fix deferred to a
  later UI/polish milestone.

## 19. V1 Exit Criteria

A scenario equivalent to:

**Administrator:**
1. Installs the APK
2. Completes initial setup
3. Enrolls the device when needed
4. Confirms Frigate connectivity

**Family member:**
1. Opens the app
2. Sees the available cameras
3. Taps a camera
4. Sees live video

**Connectivity:**
- At home: local connection
- Away from home: automatic connection through the embedded Tailscale
- The family member never needs to know which transport is used

**Definition of done:**

- All V1.0–V1.6 physical-device acceptance criteria pass
- The official Tailscale app is not required
- Frigate is not exposed publicly
- Live video works remotely for at least 5 minutes
- No reusable Tailscale auth key or secret is embedded in the APK
- No secrets (including the enrollment URL) appear in logs or the copied
  diagnostics
- The selected transport, its limitations, and the known technical debt are
  documented
- A clear go/no-go recommendation is recorded for production
